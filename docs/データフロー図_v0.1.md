# 1. 目的

本資料は、Novel Lore Manager において「誰が・どのデータを・どの処理へ渡し・どこへ保存し・何が返るか」を定義する。

画面遷移図が画面移動を示すのに対し、本資料は以下を対象とする。

- ユーザー入力
- Markdown / TXT Import
- PostgreSQL保存
- 通常検索
- Quick Recall
- Ruby / Alias / Relation
- Auto Save
- 60%版機能
- Semantic Search / Local RAG
- 将来のGoogle OAuth / MCP

---

# 2. DFD記号

| 記号 | 意味 |
|---|---|

| `-.->` | 任意・将来フロー |

# 25. 80%版：Local RAG

RAGは、質問に関係する既存資料を検索してから、その資料をLLMへ渡して回答させる方式。

```mermaid
flowchart LR
    U[ユーザー]
    UI[SCR-026 Local RAG]
    RET((Retriever))
    DB[(Entity / Document)]
    VDB[(Embedding)]
    CTX((Context Builder))
    LLM[Local LLM]
    ANSWER((Response Formatter))

    U -->|Question| UI
    UI -->|Query| RET
    DB -->|Keyword Search Data| RET
    VDB -->|Semantic Search Data| RET
    RET -->|Related Lore| CTX
    CTX -->|Question + Existing Settings| LLM
    LLM -->|Summary / Answer| ANSWER
    ANSWER -->|Answer + Sources| UI
    UI -->|結果表示| U
```

対象：

- 既存設定の検索
- 関連箇所の抽出
- 既存設定の要約

対象外：

- 本文生成
- 台詞生成
- 次話生成
- 新キャラクター生成
- 新設定の自動決定

```text
Standard Mode
    ↓

Local AI Mode
    ↓
ユーザーが明示的にON
    ↓
Local AI処理
    ↓
AI利用を画面上で把握可能
```

本ツールは利用区分そのものを自動決定しない。

# 37. Quick Recall性能方針

避ける構成：

```text
Shortcut
 ↓
Local LLM起動
 ↓
RAG
 ↓
生成
 ↓
表示
```

MVPで採用する構成：

```text
Shortcut
 ↓
Local Search
 ↓
DB Query
 ↓
Minimal Formatting
 ↓
表示
```

理由：

- 高速性
- 安定性
- AIなし利用

# 39. 作家・編集者視点の批判的検証

## 強み

- 「探す」「思い出す」を中心にしたData Flow
- Quick Recallの経路が短い
- 本文生成フローが存在しない
- ルビ・Relation・Timeline等の長編向けDataが明確
- Standard Modeが独立して成立する

## リスク

### PostgreSQLと外部ファイルの二重管理

Import後に元Markdownを編集するとDBと不一致になる可能性がある。

基本設計で、

- DBを正とするか
- File Watchするか
- 双方向同期するか

を決める必要がある。

### Asset保存方式

画像をDB内Binaryで持つか、ローカルFile + Metadataで持つか未決定。

### RAGの責務肥大化

RAGへ本文生成・設定生成まで追加すると製品コンセプトが崩れる。

既存設定参照へ限定する。

# 43. 結論

Novel Lore ManagerのMVPは、

> **入力 → 構造化 → PostgreSQL → 高速検索 → 必要最小限の参照**

を中心Data Flowとする。

Local AI / RAGは主経路を置き換えず、80%版以降の別経路として追加する。

特にQuick Recallは、

> **ユーザー → 検索 → PostgreSQL → 最小結果 → ユーザー**

という短いData Flowを維持する。
