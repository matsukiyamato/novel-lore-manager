## 1. 企画概要

### 1.1 プロダクト名

**Novel Lore Manager（仮称を継続）**。

### 1.2 コンセプト【確定】

> **書くためのアプリではない。書く手を止めないための設定管理アプリ。**

小説をPCで執筆する作者が、既に考えた設定・メモ・資料を**保存・整理・関連付け・検索・参照**できるWindowsデスクトップアプリ。小説家になろう、カクヨム、アルファポリス、Nola、秀丸、VS Codeなど**既存の本文執筆環境と併用**する。「新しい本文・設定をAIで作らせる」ことではなく、「既存の情報を迅速に思い出せる（Recall）」ことを中心価値とする。

### 1.3 開発目的【確定】

- 主目的：2028年新卒エンジニア就職活動で、要求・設計・実装・検証・改善を説明できる個人開発ポートフォリオを構築する。
- 製品目的：実際のPC小説執筆者が継続利用できる製品品質を目指す。
- 将来構想：Windowsデスクトップアプリとして販売を目指す。価格、販売チャネル、ソース公開範囲、ライセンスは**未決定**。
- 先行する目標：60%版を最初の実用到達点とし、MVPから段階的に構築する。

## 2. 開発背景と解決する問題

**ユーザーの具体的経験と旧企画書を根拠とする課題仮説**：

| 課題ID | 執筆者が困ること | 目指す改善 | 優先 |
|---|---|---|---|
| P-01 | 設定をどのファイルに記したか分からない | 横断検索・Explorer | 最優先 |
| P-02 | 設定を作ったこと自体を忘れる | Alias・カテゴリ・関連設定から再発見 | 最優先 |
| P-03 | 設定を探すため執筆画面から離れる | Quick Recallで確認して戻る | 最優先 |
| P-04 | 固有名詞の読み・ルビを忘れる | ルビ辞書・逆引き | 最優先 |
| P-05 | 人物・場所・組織の関係が増える | Relation・関連項目表示 | 高 |
| P-06 | .md/.txt/画像が分散する | Import、資料管理 | 高 |
| P-07 | 伏線・時系列・登場履歴を忘れる | 伏線管理・Timeline | 中〜高 |
| P-08 | 設定変更後に整合性を追いにくい | 更新履歴・ルール上の矛盾候補 | 中〜高 |
| P-09 | データを誤消去・破損する | Auto Save・Backup/Restore | 最優先（安全性） |
| P-10 | ファンタジー以外ではカテゴリが合わない | 共通カテゴリ・選択可能テンプレート | 高 |

上表は**ユーザーニーズ仮説**であり、各サービスの全作家が同様に困っていると断定しない。後続のユーザーインタビューと操作テストで検証する。

## 3. 想定ユーザーと対象市場

### 3.1 一次ターゲット【確定】

**Windows PCで小説を執筆し、別ウィンドウまたは別モニターで設定資料を見返す作者**。主な投稿先の想定は小説家になろう、カクヨム、アルファポリス。これらのサービスとのAPI接続や自動投稿を意味しない。

### 3.2 利用形態（直交する属性）

- **非AI利用**：自身の設定・資料を手動登録、検索・参照する。生成AIは不要。
- **AI利用**：外部AI等で作成したメモを取り込む場合や、将来Local AI機能を明示的に利用する場合がある。
- **作品規模**：短編から長編・シリーズまで対応。ただし大量設定に対する性能目標はPOCで測定する。
- **ジャンル**：異世界ファンタジーに限らず現代恋愛、青春、ミステリー、歴史、SF、ホラー、現代ドラマ、群像劇等を想定。

**未検証**：PC・スマホ・タブレット執筆者の比率と市場規模。Windows専用の方針を市場全体への適合性と混同しない。

## 4. 提供価値と製品の非対象範囲

### 4.1 主な提供価値

1. **Recall**：執筆を中断することなく設定を素早く確認。
2. **Organization**：作品内の設定の所在と分類を視覚的に把握。
3. **Reference**：人・場所・事件・組織・資料の関係を辿る。
4. **Continuity**：時系列や伏線の確認を助ける（作者の最終判断を置き換えない）。
5. **Data Ownership**：Local-firstで保存・バックアップ・エクスポートし、作品資料を作者が管理できる。

### 4.2 非対象範囲【確定】

- 本文を執筆するための長文エディタ、章の本文執筆、本文・台詞の生成、投稿代行。
- スマートフォン、タブレット、macOS、Linux向けクライアント。
- 初期フェーズのユーザー登録・Googleログイン・クラウド同期・共同編集。
- 投稿サイトが定めるAI利用区分の自動判定・適法性の保証。

**補足**：設定・メモの短い編集フォームは「本文執筆エディタ」に含めない。プロットは**プロット情報の保存・参照**であり、本文の執筆支援・自動生成へ拡張しない。

## 5. ジャンル横断の情報設計【提案】

### 5.1 共通する抽象カテゴリ

- Character（人物）
- Place（場所・舞台）
- Organization（組織・集団）
- Event（事件・出来事）
- Object（道具・物品）
- Concept（概念・制度・用語）
- Document / Note（資料・メモ）
- Other（自由分類）

**ジャンル固有の語彙はデータ属性・テンプレートで表現する**。例：国家はPlace/Organizationのいずれとして扱うか後続設計で決定し、魔法・技能・証拠・職業・研究技術などをテンプレートとして追加できるようにする。カテゴリとテンプレートを区別し、カスタムカテゴリ対応との整合を後続で検証する。

### 5.2 ジャンル別テンプレート例

| ジャンル | 追加候補となる項目 |
|---|---|
| 異世界・ファンタジー | 国家、種族、魔法、技能、宗教、武器 |
| 現代恋愛・学園 | 学校、職場、交友関係、行事、記念日 |
| ミステリー | 事件、証言、証拠、容疑者、アリバイ、時系列 |
| SF | 技術、惑星、組織、科学的制約、制度 |
| 歴史・時代 | 年号、史実、地名、出典、時代考証メモ |
| ホラー・伝奇 | 伝承、禁忌、地域、事件、怪異 |

テンプレートはユーザー入力を助けるための**任意フォーム**であり、すべての作品に項目の入力を強制しない。標準のカテゴリ数・必須フィールドは要件定義時に決定する。

## 6. 想定する中心ユーザーフロー

### 6.1 準備：設定登録

`起動 → 作品作成/選択 → 設定を直接登録 または .md/.txt をImport → 参照可能な状態で保存`

### 6.2 執筆中：即時参照

`なろう・カクヨム・アルファポリス等で本文執筆 → グローバルショートカット → Quick Recall → 語句・別名・ルビ等で検索 → 設定内容を確認 → Esc等で戻る`

ショートカット例 `Ctrl + Shift + Space` は**候補**。実際の競合・Windows側動作・元アプリへのフォーカス復帰を検証する。

### 6.3 整理：関係・時系列確認

`作品選択 → Explorer/検索 → 設定詳細 → Relation・時系列・関連メモを確認 → 必要なら編集`

## 7. 機能開発ロードマップ【新しい優先度の提案】

**60%・80%・100%は開発機能数の算術的割合ではなく、製品の到達段階を表す仮称。** 各段階は受入基準で完了判定する。

### 7.1 Stage 0：MVP（60%へ至る最初のマイルストーン）

**目的**：設定検索・参照が執筆の中断時間を減らすかを検証する。

- 作品の作成・選択
- 手動設定登録・編集・閲覧・保存
- Explorer/treeによる設定の整理と探索
- Markdown/TXT Import（原本を不用意に書き換えない）
- 通常検索・日本語全文検索（実装方式は技術検証待ち）
- Quick Recall（キーボード優先・独立した小窓を候補）
- ルビ辞書、Alias、基本的なRelation
- Auto Saveと保存失敗の明示
- Standard Mode（生成AIに依存しない）

**MVP追加検討（安全性）**：最小限のエクスポート/バックアップ経路。旧案ではBackupは60%に置いていたが、開発・利用データの消失を避けるため、MVP時点で最低限の復旧手段を確保することを推奨する。

**MVPには入れない**：音声、Local LLM、Embedding、RAG、MCP、AI矛盾判定、地図編集、Googleログイン、クラウド同期、投稿サイト連携。

### 7.2 Stage 1：60%（最初の実用到達点）

**目的**：ファンタジー以外の長編・シリーズ作品でも継続して設定を管理・参照できる。

- MVP機能の安定化、バックアップ/復元/エクスポート
- 共通カテゴリとジャンル別設定テンプレート
- 検索のフィルタ、タグ、Favorite、Recent、Backlink、カスタムカテゴリ
- Character Shelf（視覚的一覧）
- Relation Graph（登録済み関係の可視化）
- Timeline・Foreshadowing Tracker（表示・整理。本文自動生成なし）
- 画像資料・地図画像の添付/表示、マップ上の地点リンク（描画エディタではない）
- File Watch（オプション。外部変更競合時は自動上書きしない）
- Rule-based Contradiction Candidate（定義済みの形式的ルールに限定）
- Voice Recall（**追加候補**：非生成AIの音声認識を優先検証し、遅延・実装工数が厳しければ80%へ移動可能）

**60%版のリリースゲート案**：設定の登録からQuick Recallでの再発見まで一連の操作が可能、保存・復元テストに成功、通常検索でLocal LLM不使用、サンプルユーザーへの操作性評価実施。音声・グラフ等の全要素は工数検証後に最終確定する。

### 7.3 Stage 2：80%（検索・参照の高度化）

**目的**：キーワードを正確に覚えていなくても設定を見つけられるようにする。

- Embeddingによるインデックスと意味検索（ベクトル生成モデルは検証待ち）
- Local RAGによる既存設定の質問応答と**原文出典の明示**
- 軽量ローカルLLMを選択・管理する任意機能
- 通常検索とLocal AI検索を明示的に分離
- 機密設定を外部LLMサービスへ自動送信しない構成
- 60%版から繰り越した場合のVoice Recall/可視化の改善

**注記**：RAGは検索結果の取得に生成を組み合わせる手法であり、LLMの回答が常に正確とは限らない。設定そのものを根拠として表示し、作者に確認してもらう。

### 7.4 Stage 3：100%（完成・配布品質＋必要性が確認された拡張）

**必須**：Windowsインストーラ/アンインストール、更新・DB移行方針、異常終了時の復旧、ログの個人情報配慮、主要機能のテスト、利用ガイド、ライセンス確認、最低・推奨環境のベンチマーク。

**任意の高度機能候補**：AI Contradiction Candidate、Character DNA（人間が設定した人格要素を整理）、Plot Reference Board（本文編集は行わない）、Version History、高度グラフ・マップ、MCP Server・外部ツール連携。

**採否未定**：Google OAuth、Cloud Sync、複数PC同期、Pencil Sound、AIアイデア生成。特に後者は中心価値と投稿サイトのAI利用境界を踏まえて別途判断する。

100%完了条件を「候補を全て実装すること」とは定めない。製品として成立することを優先する。

## 8. AIを使わない機能と任意AI機能の境界【確定方針】

### 8.1 Standard Mode

設定登録、編集、検索、Quick Recall、Ruby、Relation、Timeline、Map、ルールベースチェックなど**実装済みのCore機能**を生成AIなしで利用できるよう設計する。AIモデルのダウンロードやGPUは必須としない。

### 8.2 Local AI Mode

ユーザーが明示的に有効化する追加機能。Local RAG・意味検索・AIによる矛盾候補などはCoreを利用するが、CoreはLocal AIに依存しない。モデル・音声認識・Embedding等のそれぞれの技術的性質と利用結果を区別する。

### 8.3 投稿サイトでのAI利用区分

アプリは作品に対するAI利用区分を自動確定しない。また**Standard Modeの使用やAI呼び出しログがゼロであることは「AI不使用」の証明にはならない**。外部での創作・AI使用状況を含む実際の制作工程を、作者自身が各サイトの最新公式ルールに照らして判断する。

**2026-10-18確認の公式参照先**：

- 小説家になろう「AI利用状況に関して」：https://syosetu.com/site/ai/
- カクヨム「小説投稿ガイドライン」：https://kakuyomu.jp/legal/guideline
- カクヨム「小説投稿ガイドラインを一部変更しました（2026-05-27）」：https://kakuyomu.jp/info/entry/gen_ai_guideline

アルファポリスのAIに関する公式分類・表示義務は本書作成時点では未検証。別途一次資料の確認が必要。

| 領域 | 現状の位置付け |

**最低動作環境・推奨環境**：現時点では未確定。Standard ModeとLocal AI Modeを分け、複数PC・GPU有無・メモリ条件・モデル量子化・応答時間を実測して決定する。ローカルLLMが動作しないPCでもStandard Modeは利用できる設計を維持する。

## 10. UI/UX基本コンセプト【提案】

- Home：プロジェクトを見つけて開くシンプルな棚型画面。Mint Complete Shelfは**UX思想の参考**とし、画像・素材・コード・特徴的画面をそのまま複製しない。
- Workspace：Explorer/treeと設定内容の2ペインを基本案とし、関連情報は必要なときに表示。ジャンル別テンプレートは編集フォームに反映。
- Quick Recall：別アプリで本文を書いている最中に呼び出し、キーボード主体で確認・終了。最初の数文字でも候補を絞り込める設計を検証。
- デュアルモニター：片側で本文、もう片側で設定参照。単一モニターでも小窓で利用できる。
- 操作性：キーボード・マウス両方をサポート。Voice Recallは補助的な手段。

具体的な画面構成とデザインはUI/UX工程で正式決定する。

## 11. 成功指標と検証方法【目標値は仮説】

| 指標 | 暫定目標 | 測定方法 |
|---|---|---|
| 設定を発見するまでの所要時間 | 既知設定で5秒以内を目標 | 課題別タスク計測。比較対象も計測 |
| Quick Recall起動 | 500ms以内を初期目標 | Windows実機で繰り返し測定 |
| 通常検索 | 500ms以内を初期目標 | 100/500/1,000件、実際の日本語データで計測 |
| 保存整合性 | 意図しないデータ欠落・上書きを防止 | 異常終了・編集競合・復元テスト |
| AI非依存性 | Core操作中に生成AI処理なし | ネットワーク遮断・モデル未導入で操作確認 |
| 汎用性 | 複数ジャンルのサンプル作品で主要情報を登録可能 | 現代恋愛、ミステリー、ファンタジー等で検証 |
| ユーザー体験 | 執筆画面への復帰が迷わず行える | 実際の執筆画面と併用してUXテスト |

これらは**企画上の初期仮説であり、製品保証値ではない**。

## 12. 競合・参考ツール

- Nola：本文執筆＋設定管理の統合ツールという比較軸。
- Obsidian / Notion / OneNote：汎用情報管理との比較軸。
- 秀丸 / VS Code：本文執筆環境との併用UX。
- ストーリープロッター / Scrivener等：小説特化ツールとの比較軸。

本製品の差別化仮説は**設定への到達速度と執筆画面との併用体験**。各競合の最新機能・価格・対応OS・利用者評価は競合調査で一次資料を検証し、優劣や市場シェアを現段階で断定しない。

## 13. リスク・制約・権利への配慮

- 未公開プロット・キャラクター設定を機密性の高いユーザーデータとして扱う。外部AI/API・クラウドへの送信は明示承認なしに行わない。
- 作品・画像・素材の著作権や利用条件を尊重する。参考UIの無断複製、他サービスの非公認自動取得を前提にしない。
- データ更新・Import・File Watchでは誤上書き防止を優先。
- PostgreSQL・Python Sidecar・TauriのWindows配布、アンチウイルス検知、サンドボックス、パス権限、DB復元の検証が必要。
- Local RAGは誤回答・引用漏れ・モデルライセンス・GPUメモリ・初回モデル取得等のリスクを持つ。
- 投稿サイトの規約と個別コンテスト規定は異なることがある。アプリは適合性を保証しない。
- 個人開発の工数制約により、100%版でも高度機能の採用は価値と実装・保守費用を踏まえて判断。

## 14. 企画から開発へ移るための工程

1. 企画書 ver2.0 レビュー・課題整理・承認
2. 要求分析書を再作成（ユーザー課題と実測・調査結果の区別）
3. 要件定義書と機能の段階別分類を再作成
4. 業務フロー・画面一覧・画面遷移・DFDを仕様に合わせて修正
5. 技術上の重大リスク（DB配布、Tauri/Backend、Quick Recall、全文検索）を早期検証する計画を立案
6. README.md更新、基本設計書v0.1、技術検証、UI/UX方針・Design System・Wireframe・Mockup
7. UI/UX確定後、基本設計書v1.0、ER/DB/API/機能/テスト等の詳細資料を整備
8. 実装直前にCodex向けAGENTS.mdを定義し、GitHub Issuesで実装・検証を管理
9. MVP実装・検証 → 60% → 80% → 100%の各段階で評価

上記は**提案する工程**。既存Repository/資料の構成変更は本書の承認後に行う。
